# Sonic Chaos ROM-derived cache

This cache contains deterministic metadata extracted from the version-checked
Sonic Chaos Master System ROM. It deliberately contains no ROM image, graphics,
tile pixels, palettes, or audio.

Every generated file records the required ROM SHA-256. Rebuild the THZ1 cache:

```bash
python tools/cache_game_data.py /path/to/SonicChaos.sms
```

`thz1/object-records.json` preserves all 53 raw nine-byte records as hexadecimal
metadata. Only types `$1B`, `$26`, and `$28` receive verified gameplay names.
Unknown types remain unnamed rather than being assigned a guessed enemy or item.

`thz1/object-21.json` records the decoded type-`$21` state table, placement-
parameter rule, reachable animation frames, and controlled original-routine
fixtures. Its possible Boing-o-Bot identity remains explicitly likely rather
than verified, so the primary identifier remains type `$21`.

`thz1/object-09.json` records all 24 one-to-one runtime entities, parameter
`$00/$01` behavior, strict collection boundaries, numeric ring-counter effect,
sparkle timing, occupancy and the proved separation from 142 layout rings.

`thz1/final-runtime-closure.json` records type-`$21` SAT bounds, block `$47`
tiles/palettes/collision and type-`$27` creation/display boundaries.
`thz1/poc-coverage.json` audits all 53 raw records exactly once against pushed
POC 18.5 and keeps object, layout-ring and terrain populations separate.

`thz1/player-state-11-graphics.json` records normal-Sonic frames
`$38/$39/$3A`: mapping records, runtime tile sources, palette, anchor geometry
and stable render hashes. `thz1/background-registration.json` records the
bounded THZ1 layout/block/tile chains and exact POC 18.5 platform-pixel
comparisons used by Task 07. Neither cache contains ROM bytes or image pixels.

`thz1/object-27.json` records the complete source-level type-`$27` state table,
strict 64/384-pixel boundaries, controlled 129-update vertical trajectory,
contact outcomes, and placement lifetime/cleanup fixtures. No semantic identity
is assigned.

`thz1/object-10.json` records all five placements, the complete four-state
table, controlled contact boundaries, exact numeric effects for parameters
`$02/$04/$06`, the direct type-`$0F` replacement path, and the distinction
between untouched respawn and consumed persistent occupancy. Monitor/item-box
presentation is supported, but no canonical semantic name is assigned.

`thz1/object-census.json` is generated by `tools/thz1_object_census.py`. It
cross-checks all 53 cached records against the matching ROM and aggregates the
existing mapping, animation, dedicated-object, recovered-region, graphics-load,
and conservative research-status metadata for all eight directly placed types.
It preserves the distinction between 24 raw type-`$09` records and 142 ring
positions decoded separately from layout blocks.

`thz1/object-10-graphics.json` is generated by
`tools/thz1_object_10_graphics.py`. It records the bank-`$0E` selector pointer
tables, raw-copy destinations and counts, tile/pixel/render hashes, palette
source, frame composition, alternate-player pointers, and the bounded type
`$05` presentation. It contains no extracted tile or palette bytes.

`thz1/closure-audit.json` is generated by `tools/thz1_closure_audit.py`. It
machine-checks the canonical census populations and records the final object,
terrain, adapter, future-fidelity and blocker classifications against POC 18.3.

`thz1/layout-interactions.json` records interaction-bearing layout cells and the
ring positions visible within the decoded ring blocks. Coordinates are direct
world coordinates after applying the established object-table `$0100` bias where
applicable.

`levels/{thz1,thz2,thz3}/` holds the act-oriented level packages (layout, rings, objects, assets,
manifest) plus `levels/object-census.json`, generated by `tools/level_export.py`; see
`docs/thz2-thz3-level-package.md`.

`thz3/object-50.json` (generated by `tools/object_50.py`) is the complete THZ3 type-`$50` study: placement,
dispatch chain, all 19 states with scripts and transitions, contact/damage/health rules, spawns, camera and
completion behavior, controlled Z80 results and emulated original-frame timelines. It stores routine regions by
offset, length, SHA-256 and a 16-byte prefix (no code dumps), the boss art by dynamic-load list and hashes (no tile
pixels), and the boss palette by index, ROM offset, SHA-256 and the three colour values that differ from the level palette.

`spring-interaction.json` (generated by `tools/spring_interaction.py`) is the complete spring model: routine hashes, the terrain handler table,
spring block/cell census, type-`$26` placements, controlled geometry/gate/parameter sweeps, launch tables, `$D448` audit, attack-posture fixtures,
emulated launches of every canonical spring cell and the original's top-of-screen/death rule. Docs: `docs/spring-interaction-audit.md`.

`levels/object-deltas.json` records the THZ2/THZ3 parameter and auxiliary-field deltas of
types `$26`, `$10` and `$28` (every placement, decoded flag bits, executed original-routine
fixtures, graphics-selector sources and the POC implementation delta list). Regenerate with
`python tools/thz2_thz3_object_deltas.py /path/to/SonicChaos.sms`.

`platform-spike-collision.json` (generated by `tools/platform_spike_collision.py`) is the platform and spike collision audit: routine hashes, the type-`$28`
platform placements and 15-state table, controlled support/gate/side sweeps, the type-`$1B` moving-spike timeline, contact cone and gates, the static
terrain-spike (type 5, blocks `$3C/$3D`) probe sweeps, the rising pass-through band, diagonal/natural-jump emulated sweeps, the damage gate and hurt
consequences, the terrain one-way block, player-state matrices, update order and the read-only POC comparison. Docs: `docs/platform-spike-collision-audit.md`.

`player-attack-badnik.json` (generated by `tools/player_attack_badnik.py`) is the player attack-posture model: `$D503` bit semantics and every
setter's exact effect, the `$D532` power-up selector, the shared `$48BC` contact rule, per-object rules for types `$21`, `$27`, `$10`, the
update order, rebound values, controlled sweeps, emulated timelines and contact trials, the POC consumer migration table and the THZ3
dependency census. Docs: `docs/player-attack-badnik-audit.md`.

`powerup-shoes.json` (generated by `tools/powerup_shoes.py`) records the complete
numeric identities and all 27 canonical placements of Rocket Shoes (type `$10`,
parameter `$04`) and Spring Shoes (mapped type `$2F`), their player-state and
RAM ownership, focused original-routine control/bounce/contact sweeps, graphics
sources, later-act reuse manifest, monitor collision-order matrix and read-only
POC migration table. Docs: `docs/powerup-shoes-audit.md`.

`thz3-boss-support.json` (generated by `tools/thz3_boss_support.py`) closes the `$1B`/`$28` cooldown, push, lifecycle and static-spike diagnostic questions and audits the THZ3
boss support chain (`$12`, `$34`, `$0A`, `$0F`), arena/camera constants, a 61,479-case boss contact grid, the defeat -> act-clear timeline, assets and the POC readiness check.
`thz3/implementation-manifest.json` is the machine-readable THZ3 manifest derived from it. Docs: `docs/thz3-boss-support-audit.md`.

`player-hurt-ring-scatter.json` records the shared hurt / lost-ring mechanic: the BCD ring-count rule (`min(7, tens + 1)`), the type-`$06` scatter object
(velocity tables, gravity, block-flag floor/ceiling probes, bounce decay, 16-update pickup lockout and pickup box, sparkle, lifetime window), allocator limits,
water independence, the second-hurt interaction and an update-aligned GPZ3 boss example. A pure-Python model is checked against the original routines
(84k ring-updates). It contains no ROM bytes beyond 16-byte prefixes and hashes.
