## Questions for Designer research
1. **Read-only source renderer map:** trace exact GameMaker viewport/application surface/window/GUI dimensions and scaling paths across accepted 348×196 Wide, actual Retro 290×218, Auto, and controlled 256×192 original reference. Include `SCR_screen`, GameMaker Windows options, texture filtering, surface blit, camera and original title/splash/UI. Distinguish source pixels from final monitor pixels; quantify present nearest-neighbour behavior, integer vs noninteger scaling, letterbox/aspect and pixel shimmer at common 1080p host sizes, without assuming the user wants 256×192 as a new selectable game mode.
2. **Scaling options:** compare native sharp nearest/integer fit, pixel-perfect integer scaling with borders, noninteger full-height/full-window fit, light postscale smoothing only if pixel-art fidelity remains intact, and careful viewport/aspect policies. Recommend which should be default **Enhanced** and whether users require explicit control/fallback. Preserve original sprite pixels, hitboxes, parallax/camera logic, no texture-byte changes. Avoid inventing a single resolution that works equally at all host ratios. The current desktop nominally 1920×1080 at 100 Hz, but this was P0 environment metadata, not a new E2 screen evaluation.
3. **CRT feasibility:** inspect intended filter candidates and license/source availability without importing code. Determine shader language, rendering passes, required persistent surfaces/buffers, alpha/order, border/overscan, scanline/phosphor/mask/gamma settings, colour management and performance on GameMaker Windows LTS `2026.0.0.23`. Establish whether current project surface ownership can accommodate it as **one outer Enhanced postprocess** without modifying frozen gameplay Draw code. Treat 8-bit fidelity, original palette and low-res UI readability as constraints.
4. **Effect isolation:** propose a single Enhanced options registry integration, safe application/restoration on mode switches/relaunch/window resize/fullscreen/cold start, and no Classic leakage. E0's registry is currently empty; never implement a dormant FX shortcut or second per-effect manager.
5. **Smallest follow-up pilot:** propose *separate* optional P1 nearest/integer scaling test and P2 CRT one-pass feasibility test if warranted, with exact new resource/change inventory, sample assets and screenshots to bring to Chief before implementation. Choose controlled sharp original-vs-enhanced pictures at same scene (GPZ3 known art discrepancy must not be presented as a filter fix). Focus on render clarity and latency/performance without pretending E1 display cadence was measured.
6. **Verification plan:** sample 348×196 Wide and actual Retro290×218, controlled reference256, keyboard/gamepad menu, title/cinematic/gameplay, Sonic/Tails, windowed/fullscreen/resizes. Verify no pixel, simulation, audio or camera changes in Classic and no per-frame resource leaks. No need for full campaigns or broad native tests in research.
