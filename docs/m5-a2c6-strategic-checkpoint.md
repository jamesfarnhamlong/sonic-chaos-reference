## B — what actual GameMaker must prove

A1P proved a real native **PSG host** in Windows GameMaker VM, using an authored
ROM-free **register script**. Its local accepted summary explicitly names that
source, and its hash is retained in [planning.json](../data/m5-a2c6/planning.json).
That is not proof of original-program decoding, SCSP loading, original stream
control flow, priority/ownership scheduling or the Python interpreter's cost
inside GameMaker. No new A1P build or runtime claim is made here.

A future gate should use a fresh isolated standalone private project; accepted
M4 and A1P are read-only references. Prefer a GML implementation of the existing
interpreter/scheduler with the accepted native PSG handoff for direct target-runtime
evidence; if a native decoding bridge is chosen instead, scope that design and
ABI explicitly. Do not embed Python, a Z80, the ROM or precombined event playback.
No particular GameMaker hashing/decompression API or speed is assumed: verify
capabilities at the new gate.

1. Load actual private **SCSP v1**, validating source/version, bounded decompression,
   canonical payload/hash, record lengths/hashes, headers, pointers and limits.
   A host-side converted event list is not a loader/interpreter demonstration.
2. Port explicit 8/16-bit wrap, signed transpose, channel byte state, shared IY,
   data-latch/DE11 protocol, priorities/mailboxes, calls/loops and verified envelope
   operations. Preserve FD scope, unsupported errors and4200-tick horizon.
3. Own a fixed60Hz sound tick and request boundary independent of variable display
   timing. The GameMaker runtime must traverse source records itself and emit ordered
   PSG bytes. Captured expected bytes are comparison-only, never runtime input.
4. Compare generated ordered bytes/ticks, all channel/global state and focused
   operations against frozen independent Python/original fixtures. Use B4 IY,
   BD actual volume entries and C2 loops; also a real THZ loop,8A held DC,
   B0/B7 equal-F3 LFSR-reset/countdown preservation and representative suppressed
   recovery/latch cases. Select a bounded subset under new authorisation.
5. Feed one persistent unchanged A1L chip. Compare continuous capture/length,
   per-voice diagnostics, counter/LFSR state and735 versus100+635 partitions.
   Request boundaries must not recreate the chip, deduplicate writes or force off.
6. Build and run in actual Windows VM, recording decoder-only tick latency,
   loading/allocation, work peaks, buffer transfer, queue/underruns, reset/restart,
   cleanup and repeated-session lifecycle. Separate these from existing PSG timing;
   Python measurements are no forecast of GameMaker performance.
7. Exercise corrupt/truncated records, bad pointer/stack/loop, unknown opcode,
   unsupported FD reader, horizon and missing terminal handling in that runtime.

or Research-main merge is part of the proposal. **STOP for Manager review.**
