# Sonic Chaos SMS research audit — 21 September 2026

## Assessment and scope

We have a reproducible, focused disassembly and behavioural reference for substantial parts of movement and terrain collision. We do not have a complete game decompilation, a complete engine translation, or a gameplay-verified Windows recreation. The strongest results are ROM-backed collision profiles, ordinary projection rules, movement constants, spring flight transitions, and a demonstrated first-curve ramp launch.

This audit inspected the local reference source, exporters, tests, reports, original partial-disassembly material, archived continuation, and GameMaker POC v14. It reran the existing ROM verification suite and assembly reconstruction. A same-day POC 15 follow-up subsequently added the verified object `$26` and `$1B` ranges and updated the current coverage figures below. The game project was not modified during the original audit.

Strictly, most of this work is **disassembly**: recovering Z80 instructions and explaining their behaviour. `tools/reference.py` translates a bounded subset to readable Python. The GameMaker project is a separate port experiment; it is not the output of a complete decompiler.

### Collision: what changed our understanding

The vertical profile is indexed by X; the horizontal profile is indexed by Y. They are distinct arrays. Sprite-mask overlap cannot substitute for the second array.

The ordinary player floor probe is at `(X,Y+18)` in the original coordinate convention; initialized side probes are `(X±9,Y+6)`, and the ceiling probe is `(X,Y-6)`. Side offsets are RAM fields and may change by context. Sprite origins from the sample engine are not automatically original player anchors.

The update sequence integrates movement, projects the floor, handles sides and ceiling/top effects, and merges contacts. Floor projection uses the **previous** surface flags before storing the newly sampled flags. If necessary it looks one tile above the sampled tile. Values above 32 must not be discarded; bit fields and low-six-bit magnitudes have defined roles.

Grounded Y movement is forced to +7, or +9 for certain modifiers, before projection. This is central to contour following. The reference does not claim all special projection branches are translated.

### First curved slope

| World tile origin | Tile | Flags | Modifier |
|---|---:|---:|---:|
| `(352,640)` | `$22` / 34 | `$83` | `$0E` / 14 |
| `(384,640)` | `$23` / 35 | `$92` | `$0A` / 10 |
| `(384,608)` | `$1F` / 31 | `$92` | `$02` / 2 |

Type `$12` dispatches to `$69B2`. With the required previous modifier, movement and contact state, the positive branch requests ramp state `$1B`. Its 8.8 arithmetic is `new_vy = -(vx + floor(vx/2))`. The negative branch first forms the magnitude, but its contact-bit gate differs: the positive branch requires combined floor contact; the negative branch returns when that bit is set. A zero-previous-modifier path instead applies a tile-selected ±4 impulse and requests rolling.

The controlled trace starts at `(320,654)` with speed +4 and held-right input. At trace frame 16, X=386, Y=643, X speed=952/256, Y speed=-1428/256, and requested state=27. It demonstrates the launch. It later shows a side contact and stopped horizontal speed; it is **not** a complete successful traversal demonstration. The fixture applies requested states directly on the following tick and omits the real animation/state interpreter.

### Movement and spring values

| Rule | Original dry value, per active update |
|---|---:|
| Ordinary airborne gravity | `$30/256` = 0.1875 |
| Upright spring ascent gravity | `$18/256` = 0.09375 |
| Ramp-launch gravity | `$24/256` = 0.140625 |
| Ordinary downward terminal speed | +7 |
| Ordinary jump launch | -4.25 |
| Upright terrain spring launch | -7.5 |
| Diagonal terrain spring in THZ | X=±4, Y=-7 |
| Diagonal terrain spring in other recovered level branch | X=±4, Y=-5.5 |
| Horizontal terrain spring | X=±6; also updates speed-cap field |

Water halves the listed airborne gravity increments in the recovered branch; ordinary jump is -3.25 and fall terminal +4. Upright ascent requests falling at its apex and sets Y velocity to +1. The empty-map fixture rises **296.25 pixels** and requests falling on active update **80**. These are routine-update measurements, not a proven PAL/NTSC frame schedule or a universal spring height across variants and collisions.

Six tables × 32 state entries × two signed increments are exported (192 rows), plus 11 surface modifiers. A modifier is a **byte offset**. The branch actually uses the no-direction table at `$439D` even on its water path; a sixth exported table is not selected by that recovered branch. Avoid assuming every apparent table is used symmetrically.

### Loops, twist and platforms

Loop paths are explicit position lookups, not ordinary slope physics. Their original fixed-point cursor loses `$000A` per update before cursor `$90`, then gains `$000C`. Right/left exits use threshold `$180`; an alternate path uses `$1A0`. Exported CSVs reach those thresholds, but the original can read an overshoot sample before checking exit. Full backing ranges are still required.

The twist uses state `$22`, four 28-entry tables (112 mappings) and tile-specific handlers. The tested vector routine multiplies a signed angle-table sample by magnitude and arithmetic-shifts by four. Two helper entry points immediately return; translating the arithmetic after those returns would invent behaviour. Some unusual entries write to ROM then fall through; their purpose is still unknown.

Platform records include lifts at `(592,464)` and `(3664,512)`. Their active movement is -1 pixel/update initially, reversing after 144 and 208 updates respectively. Four subtype `$84` platforms have an eight-pixel sag/bob limit. This does not establish a global level-time phase: activation and despawn affect when objects run.

### Layout, objects and audio

The THZ1 layout stream at file `$48000` expands to 4096 entries if read to its terminator, but the original loader stops after **4095 writes** to `$C001..$CFFF`. The decoder test protects `$D000` with a sentinel and confirms it is untouched.

The THZ1 object table at `$705AE` contains 53 nine-byte records ending at `$7078B`. X and Y each include a `$0100` bias. Later bytes are type-specific, not universally a pointer. Raw record recovery does not mean all object behaviours are identified.

All 68 SMS sound IDs `$81..$C4` match the table at `$090E1`; its stored-address-to-file conversion adds `$4000`, and the first indexed header is `$9169`. The `$A0` song/SFX division is retained from the supplied classification. No music has been rendered by this work, and the supplied Game Gear offsets remain unverified against a GG ROM.

The ramp and spring traces add assertions beyond this reported counter. Most counted cases concern lookup/side arithmetic, so this total is not an instruction-coverage or whole-game metric.

Assembly reconstruction also passed again: the final 524,288 bytes equal the supplied ROM. The build script assembles the selected 8,811 bytes and copies all gaps from the supplied ROM with `INCBIN`. This proves recovered byte identity, **not that every ROM byte has been disassembled or understood**.

The CPU harness executes original Z80 routines with supplied RAM fixtures and the mapper behaviour those routines need. It is not a complete SMS emulator: no full scheduler, VDP, PSG, interrupts, controller polling or RAM-mirroring model. No GameMaker execution is covered by these comparisons.

## Windows POC v14: concrete audit findings

The 272 embedded GML header entries exactly match the research JSON. Its first 4095 layout entries match the bounded layout. That is valid data integration. Its behaviour remains a hybrid of new Chaos routines and the sample engine. The following discrepancies were found by source inspection; none is a claim about a newly observed Windows runtime failure.

| Priority | Finding | Implication and required follow-up |
|---|---|---|
| High | The port uses one `chaosMotionState` immediately rather than the original current/requested state pair and movement/contact fields | Branch timing and animation/rolling state are not equivalent; introduce an explicit state transition step |
| High | Both ramp directions require `chaosGrounded` and use absolute X speed | The original negative branch has a different contact gate; port the actual branch structure and test both signs |
| High | Landing sets Y speed/gravity to zero, with no +7/+9 grounded integration before projection | The recovered contour-following rule is still missing; likely relevant to slopes, but runtime consequences need testing |
| High | The port returns before ramp dispatch when old flags have no projection bits | Original projection and subsequent tile dispatch are distinct stages; verify and restore their ordering |
| High | Surface modifier values are recorded but not used to apply the original horizontal increment table | Correct geometry alone does not reproduce acceleration on the curve |
| High | Ordinary side projection stops speed immediately; legacy wall checks also remain in player Step | Original merged wall contacts influence subsequent integration; use one collision sequence and timing |
| Medium | `chaosPlane` is initialized to zero with no later assignment found | Alternate headers are bundled but the player's new lookup does not execute the original plane-switch triggers; the older loop-plane system is separate |
| Medium | 4096th map entry is an added empty tile 254 and is queryable by rectangular bounds | The original lookup rejects that final RAM cell; correct the boundary rather than claiming the POC matches it |
| Medium | Gravity/impulse scale assumes 2× speed and 4× acceleration | Original active-update scheduling is not established; that scaling alone does not preserve every discrete trajectory or contact step |
| Resolved in POC 15 | V14 assigned object `$26` the terrain-spring policy by appearance/impulse shape | Bank-30 states `$8212..$8438` are now recovered and replace that provisional adapter |
| Medium | Side-probe processing only selects the direction of current motion; complete special/ceiling/top dispatch is absent from the new sequence | Special terrain cases remain outside the translated subset |
| Medium | Sprite bounding-box feet anchor the new queries | Original anchors should be represented separately from presentation and checked through animation changes |
| Open | Twist handlers were researched but not ported; loops/platforms retain earlier adaptations; test enemies remain provisional | These features need explicit implementation and gameplay comparison |

This corrects the earlier description that v14 applies the ramp state “when the original branch is eligible”: its arithmetic is grounded in the ROM, but its eligibility and scheduling are not yet faithful. Likewise, importing both planes does not mean plane switching works. We should not label v14 a validated ROM-physics build.

## What remains unknown or unverified

The main missing layer is the complete state-script/animation interpreter and its interaction with movement, not a shortage of tile artwork. We have 61 state-script pointers, but a pointer index is not an interpreter implementation. Important remaining topics include full state entry/exit effects, input/friction behaviour, all contact flag merging, special collision handlers, complete twist traversal, enemy-specific anchors/behaviours, camera activation, stage timing, and the sound driver.

Other stages, bosses, special stages, Tails-specific behaviour, power-ups such as Rocket Shoes, rendering/animation and full-game flow have not received a comparable systematic audit in this new reference. Some relevant material may already exist in the inherited source and should be consulted before further recovery.

## Recommended next work and acceptance criteria

1. **Document the movement/state update contract.** Trace the interpreter and wrappers governing standing, walking, rolling, jump, upright/diagonal springs, ramp and falling. Record current/requested state, flags and subpixel fields before and after each update.
2. **Implement one original-unit movement path.** Use 8.8 velocities and fractional position, the real input/modifier tables, grounded Y integration, and the original floor/side/ceiling/contact ordering. Keep sprite presentation separate.
3. **Compare first-curve traces before further tuning.** Cover low/high speed and both directions. A matching launch assertion is necessary but not sufficient: require matching entry, ascent, landing and stopping states, then a Windows playtest.
4. **Complete spring gameplay validation.** Preserve the upright 160-update fixture and decoded `$26` states; test all four placements plus diagonal/horizontal contact conditions and exact animation scheduling in GameMaker.
5. **Port the already-recovered twist and finish loop data.** Test entry/exit and both directions, including low speed and overshoot; do not replace source behaviour with local route exceptions.
6. **Turn the reference into the persistent project record.** Keep this audit, ROM version, region manifest, reproducible tests, explicit open questions and current POC status together. Preserve the original partial disassembly/continuation and mark superseded notes as historical.

Acceptance should distinguish four things: original bytes recovered, meaning traced, subroutine comparison passed, and full-game/Windows behaviour observed. Progress in one does not automatically establish the others.
