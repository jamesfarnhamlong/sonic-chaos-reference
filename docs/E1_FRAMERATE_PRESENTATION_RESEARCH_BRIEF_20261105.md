## Central problem — establish the *actual* current time model
Previous management shorthand called Sonic Chaos '30 FPS gameplay', while E0 design research observed the actual frozen `OBJ_chaos_zone/Create_0.gml` assigns `global.chaosTickRate=60` and `game_set_speed(60,gamespeed_fps)`; original opening, title and character choice also set 60, while the project default is 30. **Don't assume a uniform 30 Hz gameplay scheduler, a universally 60 Hz simulation, or that increasing GameMaker game speed solves smoother rendering.** Distinguish actual runner FPS, Step invocation rate, simulation advances, player/AI movement integration, render-frame counts, animation stepping, native Z80/PCM tick scheduling, camera update, v-sync and host refresh.

## Research tasks (read-only)
1. **Map every active clock/scheduler.** Inspect current E0-R1 GML, object-event registrations, `game_set_speed`, `global.chaosTickRate`, Step/End Step/Draw/Draw GUI, presentation scripts, animation stepping (`image_speed`, frame index), audio native ticks, pause/death/Continue/results/special stages/ending/title and room transitions. Prepare an ownership map with file/function paths, initialization/restoration and expected per-second rates. Classify source facts vs assumptions.
2. **Determine what the player currently sees.** Does the published Windows build actually draw new images 30, 60 or variable times per second? Does Sonic/level camera increment each Step? Are sprite animations advanced on alternate Step, per original 30 Hz state, or every Step? Check existing actual-native evidence and available timing counters first. If live measurement would require code or tooling modifications, describe the minimal future *separately authorized* instrumentation instead of implementing it now.
3. **Research possible architectures.** Compare (A) no runtime change but improved existing display pacing/VSync/present cadence, (B) 60 Hz presentation via interpolation of 30-ish logical actor/camera states at Draw only if such independent states genuinely exist, (C) explicit fixed gameplay tick(s) plus independently rendered presentation, and (D) actual 60-Hz simulation with comprehensive timing normalization (separate high-risk long-term option). Explain GameMaker runner event and frame-buffer constraints; avoid promises of independent Render events unsupported by GameMaker version.
4. **Define exact invariants.** Classic behaviour and sprites byte-for-byte protected from E0's frozen original core; Enhanced may be different in rendered positions between logical updates but must match input-state transitions, player velocity/position on canonical ticks, collisions, tile interactions, camera locks, object spawning/culling, boss timing, sound request/PSG/PCM ticks, frame-phase durations, pause/Continue/results, Special Stages and endings. No fake interpolated sprites cutting through occluders/walls, shimmer, half-pixel filtering, new latency or gameplay acceleration.
5. **Find the smallest useful future pilot.** Recommend one mode/zone and one isolated render layer (possibly camera only) using an explicitly reversible Enhanced feature ID, with Classic default untouched and user-visible fallback/compatibility if 60-Hz presentation is not viable. State required code and resource delta as a proposal only. Define side-by-side capture method (30/60/120/144Hz monitor if available), native frame/presentation timestamp logging, automated 256 control vs 348-wide comparisons, Sonic/Tails, release-like VM and GPU cost, and one small Chief A/B acceptance gate.
6. **Know the boundaries.** Evaluate GameMaker LTS `2026.0.0.23` as in accepted private build and cite actual runtime/API docs where relevant. Research how Sonic 1/2 SMS remakes achieve their '60 FPS' modes as an outside design reference only if code/docs reliable; do not assume their timing implementation matches Sonic Chaos. Do not convert this to a graphics upscale/CRT task or a generic optimization campaign.
