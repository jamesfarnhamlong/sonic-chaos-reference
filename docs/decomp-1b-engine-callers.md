# DECOMP-1B: targeted engine caller recovery

Branch `research/decomp-1b-engine-callers`, started from Research `main` `664fc4f` (DECOMP-1A merged).
Scope: find why DECOMP-1A could not reach the camera, player-update and level-header routines, recover the
smallest set of callers that fixes that, and prove each recovered boundary from the ROM. Not an attempt on the
whole main engine; no POC, root `AGENTS.md` or audit-cache changes.

Everything below is regenerated by `python tools/decomp1b_callers.py <ROM>` into `data/decomp1b/callers.json`
(deterministic, no ROM bytes) and checked by `tests/test_decomp1b.py`.

## Evidence standard

DECOMP-1A accepted an entry only when a CALL/JP sat in *byte-verified recovered assembly*. That can never reach code
whose callers are all in unrecovered engine code, which is exactly the camera/player/level set. DECOMP-1B adds one
root and keeps everything else:

* **Hardware-vector reachability** (`vector_reachability`): recursive descent over the resident engine
  (`$0000-$7FFF`) from the three vectors the machine itself defines: reset `$0000`, IM 1 interrupt `$0038`, NMI `$0066`.
  Only CALL / JP / JR / DJNZ and fall-through are followed; indirect jumps and slot-2 calls from resident code
  (bank unknown) are not. Result: 9,214 instructions, 18,642 bytes, no undecodable stop, and five indirect jumps left
  unfollowed (`$5E6F`, `$5E9A`, `$6695`, `$6972`, `$77EC`). This is *statically reachable CODE*, the same tier as
  DECOMP-1A's reviewed claims, not an execution trace.
* A region is recovered only if, from its entry points alone, confined descent fetches **every** byte as an instruction
  (so there is no embedded table or dead byte), the last instruction is terminal (no fall-through off the end), no
  recovered DATA is touched and every internal branch target is an instruction start. Boundaries between a region and
  its neighbours are entries or terminal instructions, never a guess.
* Recovered assembly stays byte-verified (`build_verify.py`); the callees it supports stay `reviewed_flow_verified`
  (`decomp1a_review.py` re-derives them to a fixed point on every build).

## Phase 1: why the priority ranges were unreachable

Every decoded call site below is in unrecovered code, so DECOMP-1A had no supported caller. All except the wrappers
are reached from the reset vector.

| Range | Entry | Decoded callers (none recovered before) | Chain from reset (transfers only) |
|---|---|---|---|
| camera update `$04C90-$04CB0` | `$4C90` | `$16CA`, `$16FA` | `$0476` -> `$2B50` -> `$2BC3` -> `$2C8A` -> `$16B8` -> `$16EF` -> `$4C90` |
| camera limit X `$04CB0-$04CF7` | `$4CB0` | `$4CA2` (inside camera update) | through `$4C90` |
| camera limit Y / VDP `$04CF7-$04D5D` | `$4CF7`, `$4D3E` | `$4CA5`, `$4CA8` (inside camera update) | through `$4C90` |
| camera follow `$05832-$05935` | `$5832` | `$4C99` (inside camera update) | through `$4C90` |
| camera follow init `$05935-$05956` | `$5935` | `$507E` (inside the level header loader) | through `$4FDC` |
| player update `$0361D-$03657` | `$361D` | 13 sites: `$0B70 $142B $1467 $14A4 $1604 $16CD $1702 $1A2A $1AA6 $1B3D $2CC7 $352B $353E` | `$0476` -> `$2B50` -> `$2BC3` -> `$2CC4` -> `$361D` |
| level header loader `$04FDC-$05082` | `$4FDC` | `$06E1` (`$06C7`), `$2945` (`$2934`) | `$0476` -> `$2B50` -> `$2B77` -> `$06C7` -> `$4FDC` |
| wrapper `$0A` `$03901-$0393B` | `$3901` | none | not reached (see below) |
| wrappers `$0E`/`$14` `$03A37-$03A59` | `$3A37`, `$3A48` | none | not reached (see below) |

The camera is a closed subtree: `$4C90` calls `$4CB0`, `$4CF7`, `$4D3E` and `$5832`, so a single supported
`$4C90` converts all of `$04C90-$05956` except `$5935`, which `$4FDC` calls. The level header loader is a leaf with
two callers.

Two drivers sit above this. The main loop at **`$1333`** (entered by `JP $1333` from boot at `$04DF` and from 11
handlers) waits for the frame (`CALL $062D`) and dispatches on `$D294` bit 7 and the bits of the flag byte `$D293`;
with no mode selected it calls the gameplay update `$16B8` and loops. A second routine chain, `$2B50` -> `$2BC3` ->
`$2C8A`, also reaches `$16B8`; it is a state loop the boot code enters first (`CALL $2B50` at `$04BE`) and is left
unrecovered.

### The wrappers are reached by script data, not by a call

`$3901`, `$3A37` and `$3A48` are the targets of three of the 69 three-byte `JP` stubs at `$0380-$044E`
(stubs `$03B3`, `$03AD`, `$03F8`). No CALL/JP/JR in the ROM targets those stubs, and none of the three reaches a
hardware vector. What reaches them is data, through an indirect jump:

1. `object_animation_engine` (`$64FA`, recovered) walks a state script. Command `FF 05` (handler `$67A1`, recovered)
   copies two script bytes into object `+$0C/+$0D` and then jumps to the selector it read.
2. Player update `$361D` calls `$5E91`, which loads `+$0C/+$0D` into HL and executes `JP (HL)` at `$5E9A`.
3. The script for player state `$0A` is word `$8142` in the type-1 state table at `$8000` (bank 12), and its bytes
   at file `$30142` are `FF 05 76 8F B3 03`: selector `$8F76`, vector `$03B3`, which is the stub `JP $3901`.
   State `$0E` (`$81E0`) and state `$14` (`$81C6`) contain `$03AD` and `$03F8` the same way; type 2 (Tails) repeats all three.

`tools/decomp1b_callers.py` records these per-state occurrences (`stub_word_in_state_scripts`); the engine facts in
steps 1-3 are asserted byte for byte in `tests/test_decomp1b.py`. This is strong supporting evidence, but not what
DECOMP-1A defines as an entry proof, and the wrappers' claim would also need the stubs themselves recovered.

## Phase 2: choosing the callers

Each candidate was simulated against the pre-DECOMP-1B evidence (`candidates` in the JSON; the same simulation
reproduces after registration because the four regions are dropped first):

| Candidate | Bytes | New supported entries | New CODE bytes classified | Chosen |
|---|---:|---:|---:|---|
| `gameplay_frame_update` `$16B8-$1753` | 155 | 7 | 569 | yes |
| `level_load_sequence` `$2934-$297E` | 74 | 2 | 199 | yes |
| `level_intro_setup` `$06C7-$0719` | 82 | 3 | 205 | no: supports the same `$4FDC` and `$59B3` as `$2934`, but its only caller (`$2B7A`) is in the unrecovered `$2B50` state loop, whereas `$2934` is called from the recovered main-loop handler `$1673` |
| `main_loop_bit1_handler` `$1673-$1696` | 35 | 1 | 6 | yes: byte-verified link between the main loop and `$2934`, plus `$59B3` |
| `main_loop_dispatch` `$1333-$1365` | 50 | 0 | 0 | yes: the main update/dispatcher; its value is the proof chain to `$16B8`, `$173F`, `$1673` |
| `mode_handler_1696` `$1696-$16B8` | 34 | 0 | 0 | no: no payoff |
| JP stub table `$0380-$044F` | 207 | 30 | 264 | no: see below |

Together the four chosen regions support 10 new entries and classify 774 more CODE bytes (the numbers above are not
additive for the two rows that share `$4FDC`).

**The stub table would be the single highest-yield dispatcher** (30 new entries and 264 new bytes, leaving 39 unresolved
clusters against 36 for the chosen set, but those entries include the wrappers this milestone could not reach). It is not recovered here because its entries are not proven in
the DECOMP-1A sense: only eight stubs have a byte-verified direct caller (`$0380 $0383 $0386 $0410 $0416 $042E $0431
$0437`) and the player-script audit cache lists eleven script vectors (this tool re-verifies the three that feed the priority
wrappers). Claiming all 69 stubs, or sixty-odd arbitrary ones, to reach the
cascade would extend a region merely for coverage. See "Next".

Neighbours are separate: `$1365` and `$1696` are other main-loop entries, the bytes before `$1673` and `$16B8` end in

## Callees converted

Ten reviewed claims were added, each re-proven by `decomp1a_review.py`: `$0361D-$03657` (player update),
`$04A74-$04AA3` (reached by the `JP $4A74` that ends player update), `$04C90-$04D5D` (four ranges, camera update, limits,
VDP hand-off), `$04FDC-$05082` (level header loader, ending in `RET` at `$5081`, immediately before the pointer table at
`$5082`), `$05832-$05935`, `$05935-$05956` and `$059B3-$059B9`. The level header loader's pointer table is not in the
claimed range and no data was claimed.

## Still unresolved from this milestone's list

* `$03901-$0393B` wrapper `$0A`, `$03A37-$03A59` wrappers `$0E`/`$14`: script-vector entries, no supported caller. They stay
  UNKNOWN in the ledger.
* Entry `$16B8`'s sibling drivers (`$2B50`, `$2BC3`, `$2C8A`) are not recovered; the vector chain through them is
  reported but not required.
* Slot-2 targets reached with an explicit bank select (`$8000` after `$1C6F`) remain ambiguous by rule.

## Next

1. **Script-vector consumer proof, then the stub table.** Walk the player state scripts with the recovered command
   handlers (record format `duration, frame, vector` and the `FF` commands) so every vector word is proven as a callback
   that `$5E9A` executes; then recover the proven stub runs (`$03AD-$03B9`, `$03C2-$03CB` are contiguous) or the whole
   table with that proof. This is the dispatcher that resolves `$3901`, `$3A37`, `$3A48`, `$3BFB` and ~25 further entries.
2. Recover the callees now classified as code (`$04C90-$04D5D`, `$05832-$05956`, `$04FDC-$05082`, `$0361D-$03657`) into
   assembly: their boundaries are now proven and they are leaf-like; this is the direct way to convert the 774 classified
   bytes into byte-verified source.
3. The startup/state loop (`$0000-$0035`, `$0476-$04E1`, `$2B50-$2CC7`) completes the byte-verified chain from the reset
   vector to the main loop.
